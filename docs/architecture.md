# 架构

## 启动链路

```
目标应用
  └─ AndroidManifest 中声明的 AppComponentFactory
       └─ 引导入口：加载内核 dex（内存加载，不落盘）
            └─ 内核初始化
                 ├─ 读取配置（模块列表、API 级别、签名信息）
                 ├─ 解包并加载 hook 引擎（LSPlant 兼容层）
                 ├─ 预置 deopt：把 Application 创建路径上的三个方法置为解释器执行
                 ├─ 重建模块 ClassLoader（见下）
                 └─ 加载模块 → 调用模块的 Xposed 入口
```

初始化顺序是刻意安排的：

1. **配置先行**：模块清单与 API 级别在加载 native 之前就确定，避免加载后才发现没有模块；
2. **hook 引擎尽早**：`Application` 创建之前必须让 deopt 生效，否则模块无法拦截应用启动；
3. **模块加载最后**：模块代码只依赖 hook 引擎与加载器，此时二者都已就绪。

## 模块 ClassLoader

Android 17 之后，模块加载器必须按依赖方向分三层（详见 `compat-android17.md` 第 4 条）：

```
PathClassLoader(模块APK, 模块APK!/lib/<abi>/)
   └─ InMemoryDexClassLoader(wrapper dex × N)
        └─ 内核 ClassLoader
```

设计取舍：

- **父加载器优先**是默认行为，所以 wrapper 加载器**不能**包含模块 dex ——
  否则模块类会被它抢先定义，随即在"读资源/加载原生库"时失败；
- 模块的原生库路径必须显式给出，直接复用 `APK!/lib/<abi>/` 的形式，不需要解包到磁盘；
- 模块资源的可用性由 `PathClassLoader` 承载，Kotlin 协程、`ServiceLoader` 等依赖
  `META-INF/services` 的库因此可以正常工作。

## 多进程

目标应用通常包含主进程与若干子进程，框架在**每个进程**都会执行初始化。
因此所有落盘动作都必须满足"多进程可并发"：

- 原生库解包使用唯一文件名（时间戳后缀），进程之间不共享 inode；
- 加载完成后立即删除临时文件，避免缓存膨胀；
- 配置读取为只读，不依赖跨进程锁。

## 日志

日志是「应用闪退之后唯一还能问话的证据」，所以写入侧只接受一种失败：所有位置都写不进去。

### 三级降级

内核与引导桩都不假设外部存储可写，按下面的顺序尝试，任意一级**真正写入成功**才停止：

| 级别 | 位置 | 说明 |
| --- | --- | --- |
| 1 | `Android/data/<包名>/.logs/<模块>/` | 首选。管理器与用户最容易取到，也是历史行为 |
| 2 | 应用私有目录：内核 `filesDir/xpatch-logs/<模块>/`，引导桩 `<dataDir>/xpatch-logs/` | 外部存储完全不可用时唯一可写的位置，只有应用自己（或 root）读得到 |
| 兜底 | logcat（tag `XPatch` / `XPatchLog`） | 上面两级全部失败时，至少把失败原因留在 logcat |

> `Android/media/<包名>/XPatch/` 是 0.1.2 之前的历史位置：内核不再写入，管理器读取与清理仍兼容。
> 判定某一级是否可用**以真实写入为准**——目录存在但被 SELinux 拒绝时继续降级，不会直接丢日志。

`<模块>` 是**模块包名**，框架自身写 `_framework`。写入失败不再静默：内核第一次写盘失败会把
原因打到 logcat（`log persistence unavailable: ...`），引导阶段则把整段堆栈写进
`bootstrap.log`（见 `compat-android17.md` 第 7 条）。

### 读取约定

- **写**：追加 + 轮转。`logs.log`、`logs_1.log`…，单文件 16 MB 封顶；写满后序号递增，
  因此**序号越大越新**（旧文件不自动删除，需要时由管理器清理）；
  同一进程内由内核侧 `synchronized` 串行化，不依赖跨进程锁；
- **行格式**：`[yyyy-MM-dd'T'HH:mm:ss.SSS] [pid:进程名] 消息`，紧随其后的缩进行属于上一条的详情；
  管理器只按这个规则切条，不解析其它格式。进程名是区分同一宿主多个进程的唯一依据，
  `:MSF` 之类子进程与主进程共用同一个 `logs.log`，没有它就无法归因；
- **读**：管理器只读不改。首屏从文件尾部按字节预算（默认 256 KB）反向分页，滚到底再沿游标
  往前推，所以「日志条数上限」不是一个配置项 —— 能翻到多早取决于磁盘，而不是常量；
- **搜索与导出**：走全量流式扫描（1 MB 一块），逐条交给回调，不把全部条目聚合进内存；
- **权限**：读其它应用的 `Android/data` 需要「所有文件访问」权限；未授权时用 Shizuku 走
  `ls` / `stat` 也能拿到同样的内容（`RuntimeLogStore.loadViaShell`）；
- **私有目录（第 2 级）管理器读不到**，只能靠应用内导出或 `adb`（debug 包）。

注意目录名是**模块包名**而不是模块显示名。同一模块作用在多个应用上时，日志分散在各应用的
`.logs/<模块包名>/` 下，管理器按「应用 + 模块」两个维度聚合，避免同名模块串台。

## 未完成部分（路线图）

### 打包器 GUI

现有工程提供的是内核与工具链。把"选择应用 → 注入内核 → 重签 → 安装"做成 GUI，
需要一套独立的打包器，计划包含：

- APK 解析与清单改写（`AppComponentFactory` 指向引导入口）；
- 内核条目注入（`assets/` 或独立目录）与对齐；
- 内置签名与签名校验（覆盖安装需要与原应用签名一致）；
- 多用户/多开场景下的安装引导。

### 原生重定向层

当前版本跳过了原生重定向层，功能主体（hook、模块、原生库）不受影响，但以下场景需要它：

- 应用自校验读取自身 APK 时，需要把读取重定向到原始（未补丁）APK；
- 部分完整性校验依赖真实 APK 的哈希/签名。

替代实现方向：以可审计的 ELF/GOT 操作库重建，或改用不依赖重定向的加载路径
（例如在类加载器层解决资源与 dex 来源）。
