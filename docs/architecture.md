# 架构

## 启动链路

```
目标应用
  └─ AndroidManifest 中声明的 AppComponentFactory
       └─ 引导入口：加载内核 dex（内存加载，不落盘）
            └─ 内核初始化
                 ├─ 读取配置（模块列表、API 级别、签名信息）
                 ├─ 解包并加载 hook 引擎（LSPlant 兼容层）
                 ├─ 预置 deopt：把 Application 创建路径上的三个方法置为解释器执行
                 ├─ 重建模块 ClassLoader（见下）
                 └─ 加载模块 → 调用模块的 Xposed 入口
```

初始化顺序是刻意安排的：

1. **配置先行**：模块清单与 API 级别在加载 native 之前就确定，避免加载后才发现没有模块；
2. **hook 引擎尽早**：`Application` 创建之前必须让 deopt 生效，否则模块无法拦截应用启动；
3. **模块加载最后**：模块代码只依赖 hook 引擎与加载器，此时二者都已就绪。

## 模块 ClassLoader

Android 17 之后，模块加载器必须按依赖方向分三层（详见 `compat-android17.md` 第 4 条）：

```
PathClassLoader(模块APK, 模块APK!/lib/<abi>/)
   └─ InMemoryDexClassLoader(wrapper dex × N)
        └─ 内核 ClassLoader
```

设计取舍：

- **父加载器优先**是默认行为，所以 wrapper 加载器**不能**包含模块 dex ——
  否则模块类会被它抢先定义，随即在"读资源/加载原生库"时失败；
- 模块的原生库路径必须显式给出，直接复用 `APK!/lib/<abi>/` 的形式，不需要解包到磁盘；
- 模块资源的可用性由 `PathClassLoader` 承载，Kotlin 协程、`ServiceLoader` 等依赖
  `META-INF/services` 的库因此可以正常工作。

## 多进程

目标应用通常包含主进程与若干子进程，框架在**每个进程**都会执行初始化。
因此所有落盘动作都必须满足"多进程可并发"：

- 原生库解包使用唯一文件名（时间戳后缀），进程之间不共享 inode；
- 加载完成后立即删除临时文件，避免缓存膨胀；
- 配置读取为只读，不依赖跨进程锁。

## 未完成部分（路线图）

### 打包器 GUI

现有工程提供的是内核与工具链。把"选择应用 → 注入内核 → 重签 → 安装"做成 GUI，
需要一套独立的打包器，计划包含：

- APK 解析与清单改写（`AppComponentFactory` 指向引导入口）；
- 内核条目注入（`assets/` 或独立目录）与对齐；
- 内置签名与签名校验（覆盖安装需要与原应用签名一致）；
- 多用户/多开场景下的安装引导。

### 原生重定向层

当前版本跳过了原生重定向层，功能主体（hook、模块、原生库）不受影响，但以下场景需要它：

- 应用自校验读取自身 APK 时，需要把读取重定向到原始（未补丁）APK；
- 部分完整性校验依赖真实 APK 的哈希/签名。

替代实现方向：以可审计的 ELF/GOT 操作库重建，或改用不依赖重定向的加载路径
（例如在类加载器层解决资源与 dex 来源）。
